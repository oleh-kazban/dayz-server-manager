How Aegis models a DayZ Dedicated Server: its files, its configuration, how it is launched, how mods are listed, and how it is stopped. The code for this lives mostly in three libraries that the server (and in two places the web app) share. For the API and the daemon see the [backend](backend.md).

## 1. What Aegis manages

| Part                | State                                                            |
| :------------------ | :--------------------------------------------------------------- |
| `serverDZ.cfg`      | Edited in the console, with validation, locking and revisions    |
| Launch command      | Compiled from stored options and mods, previewed in the console  |
| Mod list            | Workshop and local mods per server, with load order and presets  |
| BattlEye RCON       | Config generated by Aegis, client library, used for a clean stop |
| Server process      | Spawned, supervised, stopped and re-adopted                      |
| RPT log             | Tail and live stream in the API (the page is a placeholder)      |
| Central Economy     | _Planned_ (section 9)                                            |
| ADM log, world map  | _Planned_ (section 9)                                            |
| Mod downloads, keys | _Planned_ (section 5)                                            |

### Files and folders

Aegis keeps no copy of the game. A server is a registered **installation directory**, and everything else is found relative to it:

- `<install>/serverDZ.cfg` is the server configuration. The file on disk is the source of truth.
- `<install>/DayZServer_x64.exe` (Windows) or `<install>/DayZServer` (Linux) is the executable, and the install directory is the working directory.
- `<install>/profiles` is the profile directory (`-profiles=`). It holds the `.RPT` logs and the `BattlEye` folder.
- `<install>/mpmissions/<mission>` is the mission, stored as a mission template such as `dayzOffline.chernarusplus`.
- Mods are `@folder` directories in the install directory.

Windows and Linux x64 are the supported hosts. Any non-Windows host is treated as Linux. Path checks (no `..`, no null bytes, no symlink escape) live in `server-path-safety.ts` and are described in the [backend](backend.md#7-services).

## 2. `serverDZ.cfg`

`libs/dayz-config` reads, checks and writes the file. It has no dependency on Node, so the same code runs in the daemon and in the browser.

| Step        | File             | What it does                                                                                                                   |
| :---------- | :--------------- | :----------------------------------------------------------------------------------------------------------------------------- |
| Tokenize    | `tokenizer.ts`   | Splits the text into tokens, with source ranges                                                                                |
| Parse       | `parser.ts`      | Builds a `ConfigDocument`: assignments (`key = value;`, arrays `key[] = {...};`) and `class` blocks, keeping the source ranges |
| Check rules | `rules.ts`       | 59 known settings, each with a type and a range, plus the mission template and server time formats                             |
| Report      | `diagnostics.ts` | Collects diagnostics with a line, a column and a code (23 codes), severity `error` or `warning`                                |
| Project     | `projection.ts`  | Reads three values: mission template, `steamQueryPort` (default 27016), `maxPlayers` (default 60)                              |
| Template    | `template.ts`    | Renders a new file from a hostname, a mission template and a query port                                                        |
| Line ends   | `encoding.ts`    | Detects CRLF or LF and writes the file back in the same style                                                                  |

Behavior to know:

- **Strings** are quoted, and a quote inside a string is doubled (`""`). A template field with CR, LF or a null character is rejected.
- **Unknown or duplicate settings** are warnings, not errors. A value of the wrong type is an error. A number outside its range is an error when the rule is strict (`maxPlayers`, for example) and a warning otherwise. A value that differs from the recommended one is a warning (`NON_RECOMMENDED_VALUE`).
- **The database keeps only the projection** (mission template, query port, max players) of the file, as a read-only copy. The file stays the source of truth.
- **Both sides run the same checks.** The web editor calls `analyzeServerConfig` on the text as the operator types, and the daemon runs it again on save. The daemon adds two checks that need the disk and the other servers: `MISSION_NOT_FOUND` and `STEAM_QUERY_PORT_CONFLICT`. The browser never reports those two.
- **Editing rules** (stopped server only, lock with a 120 s expiry, atomic write with a backup, one revision per write, 64 KiB limit) are in the [overview](overview.md#configuration-files) and the [backend](backend.md#7-services).
- **Creating the file** (`bootstrap`) writes a template only when `serverDZ.cfg` does not exist.

## 3. Launch command

`compileLaunchCommand` (`libs/dayz-config/src/lib/launch/compiler.ts`) turns a server's settings into the process to spawn. It is pure: the same input gives the same output. The daemon uses it for the preview endpoint and for the supervisor, and the web app uses it for the live preview in the launch options card. The daemon tells the browser which host platform to compile for.

**Arguments**, in this order:

1. Managed by Aegis: `-config=serverDZ.cfg`, `-port=<gamePort>`, `-profiles=<profile directory>`, `-BEpath=<profile directory>/BattlEye`.
2. Mods: `-mod=@a;@b` and `-serverMod=@c`, from the mod list (section 5).
3. Operator options: `-cpuCount=`, `-limitFPS=`, `-doLogs`, `-adminLog`, `-netLog`, `-freezeCheck`, `-scriptDebug=true`, `-filePatching`.

**Operator options** are a closed set of eight (`launchOptionsSchema`, strict): two numbers (`cpuCount`, `limitFPS`) and six switches. There is no free-text argument field, by design. New servers start with `cpuCount=4`, `doLogs`, `adminLog` and `netLog` on.

**Safety:**

- The result is `ready: false`, with no arguments, when the install path is not absolute for the platform or contains `..` or control characters, the profile path is not a safe relative path, the port is outside 1024 to 65535, a mod folder name is invalid, or the options do not parse.
- Every emitted argument must match `-flag` or `-flag=value` with no control characters or quotes, or the whole command is refused.
- `commandLine` is for display and copy only. The supervisor spawns `executable` with the `args` array and never runs that string.
- Warnings (not errors): `-filePatching` (loads unsigned data), `-scriptDebug` (costs performance) and enabled mods with no folder name.

## 4. Server process

`libs/platform` hides the operating system behind `ProcessManager`. The state machine and the stop sequence are in the [overview](overview.md#server-process-supervision).

- **Spawn:** detached, with a hidden window on Windows, with an argument array.
- **Identity:** a process is a `pid` plus a `startToken` taken from the OS start time (`win32:<creation time>` through CIM, `linux:<start time>` from `/proc/<pid>/stat`). A reused pid with another start time is not the same process, so Aegis never kills a stranger.
- **Kill:** Windows ends the whole tree with `taskkill /T /F`. Linux signals the process group: `SIGTERM`, then `SIGKILL` after a 10 s grace, and confirms the exit within 5 s.
- **Re-adoption:** the pid, start token and start time are stored with the server, so a restart of Aegis finds the running server again (`reconcile`).

## 5. Mods

Mods are rows of `server_mods` (see [persistence](persistence.md#3-tables)).

| Field                  | Meaning                                                                                                                                        |
| :--------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------- |
| `sourceType`           | `workshop` (a Steam Workshop item) or `local` (a folder the operator manages)                                                                  |
| `workshopId`           | The Steam item id: 1 to 20 digits                                                                                                              |
| `folderName`           | The `@folder` name in the install directory: starts with `@`, at most 128 characters, no `;`, `/`, `\` or `..`                                 |
| `loadTarget`           | `client_server` goes to `-mod=`, `server_only` goes to `-serverMod=`, `client_optional` is never loaded by the server                          |
| `enabled`, `loadOrder` | Only enabled mods are launched, in load order                                                                                                  |
| Sync fields            | `remote_updated_at`, `synced_workshop_updated_at`, `last_synced_at` give the status: `up_to_date`, `update_available`, `not_synced` or `local` |

What works today:

- **Lookup and search** of Workshop items and collections through the Steam Web API, with the key stored encrypted in `steam_settings`. A request times out after 10 s, a batch is 50 items, a collection up to 200.
- **Add, batch add, edit, remove and reorder** mods, with keyboard and drag-and-drop ordering in the console.
- **Update check** against the Workshop (`check-updates`).
- **Presets.** Export and import use a DayZ Launcher style preset with `steamWsMods` and `steamWsServerMods`, up to 300 items. _Merge_ appends new mods after the last one and skips ids the server already has. _Replace_ makes the Workshop mods match the preset: existing mods are updated in place (folder, enabled flag and sync state survive), missing ones are removed, new ones are added, and local mods keep their slots.

What does not exist yet:

- **Downloading** mods with SteamCMD, with progress (`DSM-00133`). The operator places the `@folder` on disk today.
- **Keys.** DayZ checks a player's mod signature against a `.bikey` file in the server's `keys/` folder. Aegis does not touch that folder yet. _Decided:_ Aegis **copies** a mod's `.bikey` into `keys/` when the mod is enabled and removes the copy when the mod is disabled or removed (`DSM-00337`, `DSM-00338`). It does not use symlinks or hardlinks: creating a symlink on Windows needs an administrator or Developer Mode, and a hardlink works only inside one volume and keeps pointing at the old data after an update. Aegis records what it copied (key name, source and hash), copies again when a mod update changes a key, and removes only its own copies, never the vanilla keys. Two mods that ship a key with the same name, and a key renamed by an update, still need rules when this is built.

## 6. BattlEye and RCON

**Config.** Aegis generates the BattlEye RCON config, operators do not edit it. The file goes in `<profile directory>/BattlEye/` and is named `BEServer_x64.cfg` on Windows and `beserver_x64.cfg` on Linux. It holds `RConPassword`, `RConPort`, `RConIP` and `RestrictRCon 0`. Leftover `BEServer_x64_active_*.cfg` files from earlier runs are removed, and a replaced file is backed up first. The password is printable ASCII only (BattlEye's rule) and is stored encrypted ([persistence](persistence.md#4-secrets-and-hashes)). It is written to the file when the server is saved and when `battleye/sync` is called.

**Client.** `libs/rcon` implements BattlEye RCon v2 over UDP: a login handshake, commands with sequence numbers, multi-part response reassembly and typed results (no exceptions for network outcomes).

- A login fails with `login_failed`, `timeout` or `unreachable` (the operating system reports an ICMP "port unreachable" on the connected socket).
- A command waits 2 s for an answer and is sent again up to 2 more times, then fails with `timeout`. Other failures are `not_logged_in`, `connection_lost` and `busy`.
- The password stays outside the client object and is never logged or returned.

Today the only command Aegis sends is `#shutdown`, in the graceful stop. Player lists, kicks, bans and messages are not built.

## 7. Logs

- **RPT** (the engine log, `*.RPT` in the profile directory): the daemon finds the newest file, reads its tail on demand and follows it live (`log.lines` events). If the server has not written a file yet, the follower waits. The `LogViewer` colors a line as an error or a warning by matching the words `error`, `exception`, `fatal`, `crash`, `warning` and the script markers `(E)` and `(W)`. The page itself is a placeholder.
- **ADM and script logs:** _planned_ (`DSM-00212`, `DSM-00213`). The `adminLog` launch option already makes the server write the ADM file.

## 8. Web and server drift check

Compared on 2026-11-24:

- The launch compiler and the config checker are one library used by both sides, so the rules cannot differ. The only difference is the two disk-dependent diagnostics, which only the server reports.
- Defaults for new servers are consistent: game port 2302 and RCON port 2310 in the contract, the database and the create dialog (written in each place, see TD-12), query port 27016 (in the route and in `libs/dayz-config`, also twice).
- The stop delay presets and limits, the config size limit and the mod rules come from `libs/api-contracts` for both sides.

## 9. Planned and undecided

These come from the old design and the [backlog](../product/backlog.md). None has code yet.

- **Central Economy.** A workbench for `types.xml` (loot table: `nominal`, `min`, `lifetime`, flags, `category`, `usage`, `value` tiers), `cfgspawnabletypes.xml` and related files. The old design lists these rules: `min` must not exceed `nominal`, `lifetime` must be positive, filters by category, usage and tier, bulk edits with percentages, a clean XML write that keeps formatting and comments, and a backup before every write. Backlog: `DSM-00222` to `DSM-00231` (a spike on parsing large files in a worker comes first).
- **ADM parsing.** Player events with coordinates, chat and kills, from the ADM log. Backlog: `DSM-00212`.
- **World map and loot heatmap.** DayZ coordinates start at the south-west corner, with Y growing to the north, so a map layer must flip Y. Map sizes and the loot point source (`mapgrouppos.xml`, `mapgroupproto.xml`) are to be checked when the map is built. Backlog: `DSM-00141` and its stories.
- **Server FPS from the RPT log, telemetry, the A2S query and a watchdog.** Backlog: `DSM-00114`, `DSM-00139`.
- **Key handling for mods**, see section 5 (decided, not built).
